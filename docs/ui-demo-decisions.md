# Stack UI 데모 — 임시 결정 및 미확정 목록

> 기준: `PRD-v0.2.md`(기능·정책), `DESIGN.md` v0.2.1(시각·상호작용). 이 문서는 PRD를 변경하지 않으며, UI 데모에서 불가피하게 둔 **임시 선택**과 PRD의 **미확정 항목**만 기록한다. 제안은 확정 정책으로 승격하지 않는다.

| 결정 | 내용 | 비고 |
|---|---|---|

### 4단계 결정 (선택 · 모의 서재 · 리더 진입)

| 결정 | 내용 | 비고 |
|---|---|---|
| 선택 위치 | 홈 카드의 "선택하기"와 상세 미리보기의 "이 자료 선택하기". 버튼 바로 아래에 "선택한 학습 자료는 변경할 수 없어요."를 상시 노출 | 선택 확인 모달은 쓰지 않음(PRD 미확정, 상시 안내로 갈음) |
| 선택 제약 | 추천 묶음(세트 id)당 1개. 같은 자료 중복 선택은 기존 기록을 돌려주고, 같은 묶음의 다른 자료 선택은 거절한다. 변경·취소·추가 선택 UI 없음. 선택 후 다른 카드는 비활성 + 이유 문구 | 규칙: `src/lib/selection-rules.ts`. 모의 저장 지연 350ms + 화면의 진행 중 차단(빠른 중복 클릭 1건) |
| 선택 ≠ 시작 ≠ 완료 | 선택은 `selectedAt`만 기록. 리더에 처음 들어올 때 `startedAt`을 한 번 기록(서재 '읽는 중'). `completedAt`은 5단계의 명시적 완료에서만 | 리더 진입·스크롤·시간으로 자동 완료하지 않음 |
| 후보 1개일 때 선택 | 임시로 허용 | PRD D-09 미확정 |
| 서재(최소) | 선택한 자료 목록과 상태(선택함/읽는 중), 학습 시작·이어서 읽기 링크. 삭제 기능 없음, 빈 상태에서 홈 이동 | 회고 확인·완료 표시는 이후 단계. 확정 전에도 URL로 열림(§9.3 확인 필요) |
| 이어서 읽기 | 홈의 오늘의 추천 아래. 완료하지 않은 선택 자료를 최근 순으로. 선택한 자료가 없으면 영역 생략 | 읽던 위치 복원은 P1이라 하지 않음 |
| 리더 진입 | `/read/[id]`. 선택한 자료만 열림(미선택·없는 자료·확정 전은 안내 또는 온보딩 이동). 하단 탐색 숨김, 이전(←) 버튼 | 4단계에서는 본문 자리에 안내만 두었고, **5단계에서 본문과 학습 완료로 대체됨** |

### 가운데 점 사용 금지 (사용자 지시, 5단계 적용)

사용자 지시에 따라 사용자에게 보이는 모든 화면의 문구와 메타데이터에서 가운데 점 문자 `·`와 `ㆍ`, 구분용 `•`를 쓰지 않는다. PRD와 DESIGN 원본은 수정하지 않았고, 이 지시를 구현 코드와 이 기록에 반영한다.

| 적용 | 내용 |
|---|---|
| 구분 방식 | 유형, 주제, 시간은 간격과 별도 요소로 구분(`flex`와 `gap`). 문장에서는 쉼표나 "와", "과" 같은 연결어. 상태 구분은 마침표나 콜론 |

### 고민 칩 선택지 5~8개 보강 (2026-10-16, 사용자 요청, PRD 원본 미수정)

최대 선택 수 3개와 기타 제한 제외, 3개 선택 시 나머지 비활성, 해제 후 재활성은 그대로다. 표시할 선택지 수만 늘렸다. 기존 15개의 key와 라벨, 저장 데이터의 칩 key는 바뀌지 않았다. 새 항목 12개는 목록 뒤에 붙였고, 그룹 안에서는 기존 항목 다음에 표시된다. PRD D-27(칩 구체 목록)은 이 표가 현재 구현 기준이다. PRD에 반영하려면 새 버전이 필요하다.

| 카테고리 | 최종 칩 (key) | 개수 |
|---|---|---|
| 문제 정의와 리서치 | 사용자 리서치 (user-research), 문제 정의 (problem-definition), 데이터 해석과 지표 설정 (data-metrics), 새: 페르소나와 사용자 여정 (persona-journey), 경쟁 서비스 분석 (competitor-analysis), 가설 세우고 검증하기 (hypothesis-test), 사용성 테스트 (usability-test) | 7 |
| 설계 | 정보구조와 플로우 설계 (ia-flow), UI 디자인 (ui-design), 디자인 시스템 (design-system), 인터랙션과 프로토타이핑 (interaction-prototype), UX 라이팅 (ux-writing), 새: 접근성 고려 (accessibility), 예외 상황 설계 (edge-states) | 7 |

선정 기준: 취업 준비생(이력서, 과제 전형)과 주니어 실무자(실무 적응, 성장 계획, 리뷰, 전달 문서)에 모두 맞는 구체 업무로 하고, 기존 항목과 뜻이 겹치는 이름(예: 인터뷰 질문 설계, 일정 조율)은 넣지 않았다. 설계와 협업은 개수를 다 채우지 않고 각각 7개와 6개에서 멈췄다.

토픽 연결:
- 새 key는 칩 key가 곧 학습 주제 key라서, 모의 분석의 후보 주제와 확정 방향의 세부 주제(추가 목록 포함)에 그대로 쓰인다. 각 항목의 한 줄 설명은 `TOPIC_WHY`(`mock-analysis-fixtures.ts`)에 추가했다.
- 분석 결과의 핵심 방향은 첫 번째로 고른 칩의 카테고리 기준 문구를 쓴다(카테고리 문구는 기존 그대로).
- 예시 자료 11개의 주제 태그는 바꾸지 않았다. 새 주제에 맞는 자료는 아직 없으므로 새 칩 3개만 골라 확정하면 추천이 비고 기존 "관련 없는 자료로 채우지 않았어요" 후보 부족 안내가 나온다(확인함). 새 칩 1~2개와 기존 칩을 함께 고르거나 같은 카테고리의 기존 주제가 후보에 들어오면 기존 자료가 추천될 수 있다. 자료는 새로 만들지 않았다.
- 후보 자료 확충이 필요하면 별도 작업이다(미착수).

### 추가 설명의 분석 반영 (후속 구현 항목, 2026-10-16)

- 3단계 서브텍스트에 "입력한 내용은 학습 방향 분석에 참고해요"를 표시한다. 추가 설명을 분석에 활용하는 것은 기존 PRD 요구사항(F1-01, F1-04)이다.

## 리더 원문 기반 개편과 실제 학습 시간 기록 (2026-10-17, 사용자 요청)

배경 #F2F4F6 변경, 남은 공통 글자 크기 조정, 주의 아이콘, 서재 디자인, Mixpanel 연결, 새 추천 방식, 새 라이브러리는 이번에 하지 않았다. 추천 선정과 교체 규칙, 세트당 선택 1개, 서재와 재열람 규칙, 명시적 "학습 완료"만 완료로 인정하는 규칙, 저장 중 중복 실행과 실패 처리는 바꾸지 않았다. 기준은 `docs/ui-style-guide.md` 16번, `PRD-v0.10.md`, 조사와 출처 기록은 `docs/recommendation-gap-analysis.md`와 `docs/content-sources.md`.

### 1. 추천 공백 조사

원인은 두 가지로 구분된다. ① 주제 자료 부족(고민 칩 27개 중 13개 주제에 자료 0개), ② 회차 소진(직전 추천과 선택한 자료를 빼면 후보가 2회차 안에 바닥남). 대표 조합 20개 중 1회차에 2개를 받는 것은 9개, 2회차에는 16개가 0개다. 규칙은 바꾸지 않았고 자료를 일괄 생성하지 않았다. 보강 우선순위는 사용성 테스트, 접근성 고려, 그다음 자료 0개 주제들이다. 자세한 표는 조사 문서에 있다.

### 3. 리더

- 구성과 문구는 스타일 문서 16번과 같다. 본문 16px, 행간 1.75, 왼쪽 정렬로 예시 자료 본문도 함께 맞췄다(이전 18px/32px). 본문 카드나 외곽 스트로크 추가 없음.
- 예상 시간은 "Stack 요약 읽는 시간 약 4분"(요약 약 1,500자 기준 추정)이고 미니미션은 약 10분(선택).
- 선택 입력은 `stack-demo:v1:reader-notes`에 자료별로 저장한다(최대 2000자, 0.6초 입력 정지, 숨김, 이탈 때 저장). 선택한 자료에만 저장하고 외부로 보내지 않는다(요청 로그로 확인).
- "읽기 완료"라고 부르신 버튼은 기존 이름 "학습 완료"를 유지했다(다른 화면과 용어 일치).
- 데모 안내 문구 두 곳이 "읽기 시간 측정은 아직 없다"고 말하고 있어 사실과 맞게 고쳤다(홈, 리더). 서재 안내의 "회고" 문구도 정리.

### 5. 학습 스택

한국 시간 날짜 기준으로 바꿨다(이전: 브라우저 로컬 날짜, `buildStackDays`는 이제 현재 시각을 ms로 받음). 단계와 색, 범례, 안내 문구, 접근성 텍스트는 스타일 문서 16번과 같다. `active`(학습한 날)는 5분 이상만이라 "학습한 날 N일"은 5분 이상인 날만 센다. 잔디 칸 `data-stack-cell` 값은 `inactive`, `progress`, `active`.

### 검증 (390px, 시간 제어, 빈 저장소의 새 브라우저 컨텍스트)

- 시간 제어는 Playwright `page.clock`과 숨김, 포커스 이벤트 모의로 했다(실제 5분을 기다리지 않음). 59초 59,000ms(빈 칸), 60초 60,000ms(학습 진행), 299초(학습 진행, "4분 59초"), 300초(학습한 날) 기록과 스택 칸 색을 확인. 숨김 10분과 포커스 없는 5초는 더해지지 않음(10초 + 4초만), 자정(23:59:30에서 60초)은 30초와 30초로 분할, 30분 점프는 세지 않음.
- 두 탭을 실제로 동시에 약 7초 열었을 때 합계 8.4초(경과 7.8초 이하 허용 범위)이고 중복 합산 없음. 외부 원문 탭 2분은 시간 불변(숨김과 포커스 상실 모의), 리더를 벗어나면 30초가 지나도 불변, 완료 버튼은 시간 불변.
- 리더: 순서, 출처와 발행일, 원문 보기(URL, 새 탭, noopener, 기존 리더의 입력 유지), 본문 16px/28px 왼쪽 정렬, 문단이 본문 전체 폭, 카드 없음, 가로 넘침 없음. 입력은 새로고침 후 복원, 외부 요청 없음, 빈 입력으로 학습 완료, 완료 후 서재에서 다시 열면 입력과 완료 상태 유지. 예시 자료는 미션과 회고와 입력창과 원문 보기가 없음.
- 단위 테스트 160개(시간 분할, 누적, 일시정지, 복수 탭, 복원, 단계 경계, 원문 자료 무결성, 추천 관련성, 입력 저장 규칙), 린트, 타입 검사 통과.

### 남은 제약

- 실제 탭 전환과 새 탭 열기에서 브라우저가 `visibilitychange`와 포커스를 주는지는 브라우저와 OS에 달려 있다. 자동 검증은 이벤트를 모의했고(헤드리스 브라우저는 모든 탭을 보이고 포커스 있는 것으로 보고), 실제 브라우저 확인은 못 했다.
- 시계는 브라우저 시계이며 사용자가 바꿀 수 있다(서버 시각 기준이 필요, PRD 14.6). 앱 강제 종료로 마지막 최대 5초가 유실될 수 있다.
- 시간은 초 단위 소수 버림으로 표시한다. 같은 날 같은 자료를 여러 번 읽은 시간은 모두 합산한다.
- 미리보기와 홈 카드에는 원문 출처 표시가 없다(요청 범위 밖). 원문 URL의 유효성은 운영 점검이 필요하다. 원문 글은 2000년 글이다.
- 미니미션과 회고가 사용성 테스트 자료 하나에만 있다. 리더 안 회고와 PRD의 완료 후 회고(F3-03)의 통합 여부는 미정.


## 새 회차 재추천 규칙, 원문 자료 3개, 개발 확인 경로 확장 (2026-10-17, 사용자 요청)

**목표**: 확정한 학습 주제가 있는데 추천이 비어 학습을 시작하지 못하는 문제를 줄인다. 화면 장식이나 다른 기능은 추가하지 않았다.

**현재 상태와 원인(다시 확인)**: 코드와 자료로 다시 세어 보았다. 변경 전에는 UX 라이팅 자료 0개, 개발자 협업 자료 1개였다. 새 회차에서 직전 추천과 선택한 자료를 모두 빼므로 후보가 바닥나면 0개가 됐다. 개발용 리더가 일반 홈을 바꾸는 문제는 재현되지 않았다(사용자 저장소 키 전후 비교). 실제 사용자 브라우저의 정확한 빈 상태 원인은 저장 데이터를 읽지 못해 확정하지 못했다.

**추천 규칙(변경 전후)**
| | 변경 전 | 변경 후 |
|---|---|---|
| 같은 회차 | 저장된 묶음을 그대로 보여 줌 | 같음(재진입, 새로고침으로 안 바뀜) |
| 새 회차 후보 | 관련 자료에서 직전 추천과 선택한 자료를 모두 뺌 | 관련 자료에서 선택한 자료만 뺌. 직전 추천에 없던 자료를 먼저 쓰고, 2개를 못 채울 때만 직전 추천 중 선택하지 않은 자료로 부족한 수를 채움 |
| 추천 수 | 2개 | 2개(`RECOMMEND_TARGET`, 늘리지 않음) |

| 같은 묶음 중복 | 없음 | 없음 |
| 0개 안내 | 한 가지 문구 | 자료 없음, 관련 자료를 모두 선택함, (이전 규칙으로 만든 묶음의) 직전 추천이라 빠짐을 구분 |

구현: `pickRecommendations(catalog, topicKeys, excludeContentIds, deprioritizeContentIds)`가 두 단계(신규, 직전 추천)로 같은 정렬(겹친 주제 수, 목록 순서, 두 번째는 가능하면 다른 유형)을 적용한다. 홈은 새 회차를 만들 때 선택한 자료를 제외로, 직전 묶음의 자료를 미루기로 넘긴다. 현재 회차의 기존 묶음을 강제로 다시 만들지 않으며 사용자 저장 데이터를 지우지 않는다. 이미 0개로 저장된 묶음은 다음 회차(오후 6시)에 새 규칙으로 바뀐다.

**원문 기반 자료 3개 추가**: 원문을 직접 열어 확인한 것만 썼다. 상세와 한계는 `docs/content-sources.md`. 원문 주장과 Stack의 적용 제안을 요약과 연결 설명으로 구분했고, 미니미션은 Stack이 제안한 연습이며 채점이나 AI 피드백이 없다. 예상 시간은 요약 분량 기준이다. 예시 자료를 원문 기반으로 바꾸거나 주제 태그를 넓히지 않았다. 자료 id 3개: `nng-error-message-guidelines`, `hse-error-message-ux-writing`, `figma-designer-developer-handoff-handbook`.

**대표 조합 20개 검사**: `node scripts/recommendation-gap.mts`(표는 `docs/recommendation-gap-analysis.md`). 실패 0건. 후보가 없는 주제 10개는 그대로 남겼다.

**개발 확인 경로 확장(최소 재사용)**: 기존 `/dev/reader`(사용성 테스트 자료 고정)는 그대로 두고, 같은 `DevReaderScreen`을 자료 id별로 여는 `/dev/reader/[id]`를 더했다. 원문 기반 자료 4개만 열린다. 저장 분리(접두어 `stack-dev-reader:`), 완료 전 상태 초기화는 기존 그대로이며 실제 사용자 기록과 운영 접근 제한은 바꾸지 않았다. 운영 빌드는 `NODE_ENV`가 production이면 404.

**검증**: 격리된 새 브라우저(390px)에서 개발 확인 경로 3개(원문 링크, 출처, 요약 연결 미션 회고, 가로 넘침 없음, 입력 재진입 유지, 초기화, 비운 채 완료, 실제 저장소 키 변경 없음)와 일반 흐름(UX 라이팅 홈 카드, 미리보기, 선택, 리더, 같은 회차 새로고침 유지, 다음 회차 신규 우선과 선택 자료 제외, 개발자 협업 추천에 Figma 자료와 미리보기)을 모두 통과했다. 단위 테스트 추가, `tsc`와 lint 통과.


## 접근성 고려 원문 자료 3개와 기존 자료 검수 (2026-10-17, 사용자 요청)

접근성 고려 후보 0개가 보강 1순위여서 W3C 문서 3개(글자 대비 기준, 키보드 포커스 설계, 폼 알림)를 원문 기반 자료로 추가했다. 세 자료는 시각, 상호작용, 폼으로 학습 목적이 다르고 태그는 모두 접근성 고려 하나만 붙였다. 출처, 확인 내용, 한계와 앞서 만든 4개 자료의 검수 결과(HSE 자료의 접두 번호 표기 1건 수정)는 `docs/content-sources.md`, 대표 조합 20개의 재검사는 `docs/recommendation-gap-analysis.md`에 있다. 추천 규칙, 공통 스타일, 완료 모달, 학습 스택, 저장 기록은 바꾸지 않았다. 개발 확인은 기존 `/dev/reader/[id]`를 그대로 썼다(코드 변경 없음). 검증: 390px 격리 브라우저에서 세 자료의 원문 링크, 출처, 요약과 연결과 미션과 회고, 가로 넘침 없음, 입력 재진입 유지, 초기화, 비운 채 완료, 실제 저장소 키 변경 없음 통과. 일반 흐름에서 접근성 고려만 확정하면 홈에 2개가 추천되고 같은 회차 새로고침에도 유지되며, 다음 회차에는 선택한 자료를 빼고 신규 자료를 먼저 쓴 뒤 직전 추천의 미선택 자료로 보충했다.


## 개발용 전체 흐름 `/dev/home` (2026-10-17, 사용자 요청)

**목적**: 저장된 추천 상태 때문에 새 콘텐츠가 일반 홈에 보이지 않아도, 실제 사용자 기록을 바꾸지 않고 홈부터 전체 학습 흐름을 반복해서 확인한다.

**구조(복제 없이 재사용)**
- 실제 `HomeGate`, `PreviewScreen`, `ReaderScreen`, `LibraryScreen`과 추천 함수를 그대로 쓴다. 화면이 쓰던 `getRepository()`와 하드코딩된 경로를 `ReaderEnv` 컨텍스트(저장소, 읽기 시간 저장소, 경로)로 바꿨고, 기본값은 이전과 같은 실제 저장소와 실제 경로라서 운영 화면의 동작은 그대로다.
- 개발 환경에서만 `/dev` 레이아웃(`DevFlow`)이 접두어 저장소(`stack-dev-home:`)와 `/dev` 경로 집합을 컨텍스트로 넣는다. 그래서 `/dev/home`, `/dev/library`, `/dev/content/[id]/preview`, `/dev/read/[id]` 사이를 오가도 같은 개발용 저장소를 쓰고, 실제 경로(`/home` 등)는 컨텍스트가 없어 실제 저장소만 쓴다. 일반 서비스로는 "일반 서비스로" 버튼으로만 돌아간다.
- 기존 `/dev/reader`와 `/dev/reader/[id]`는 원문 기반 자료 단독 확인용으로 유지했고 접두어(`stack-dev-reader:`)가 달라 서로 기록을 지우지 않는다.
- 데모 안내(`DemoNotice`)는 `/dev` 경로를 같은 화면의 안내로 처리한다.

**시나리오와 초기화**: UX 라이팅, 개발자 협업, 사용성 테스트, 접근성 고려. 시나리오를 고르면 개발용 접두어 키를 비우고 그 주제만 확정된 가짜 학습 방향을 저장한다. 추천 묶음은 만들어 넣지 않고 홈이 실제 추천 함수로 만든다(특정 카드를 끼워 넣지 않음). "테스트 상태 초기화"는 현재 시나리오를 같은 방식으로 다시 만든다. 지우는 범위는 `clearPrefixed`로 접두어가 같은 키뿐이며 리더를 먼저 내려 읽기 시간의 마지막 구간을 저장한 뒤 지운다. 개발용 화면이 아닌 곳에서 초기화하면 개발용 홈으로 이동한다.

**운영 정책 유지**: 추천 규칙, 선택 제한(회차당 하나, 선택 불변), 학습 시작 확인, 완료 처리, 읽기 시간 집계는 그대로이고 개발용을 위해 완화한 것이 없다.

**운영 차단**: 모든 개발용 페이지와 레이아웃이 `NODE_ENV`가 production이면 `notFound()`를 호출한다. 격리 작업공간(저장소 복사본)에서 빌드하고 `next start`로 실제 요청을 보내 `/dev`, `/dev/home`, `/dev/library`, `/dev/reader`, `/dev/reader/[id]`, `/dev/content/[id]/preview`, `/dev/read/[id]` 모두 404이고 실제 경로는 200임을 확인했다.

**자동 검증(390px, 480px)**: 시나리오 선택, 추천 카드, 미리보기, 학습 시작 확인, 리더, 완료, 서재, 뒤로가기, 미션과 회고 입력과 새로고침, 읽기 시간, 초기화, 시나리오 전환, 일반 서비스로 이동, 같은 회차 새로고침 시 추천 유지, 모든 단계에서 실제 저장소 변경 없음, 가로 넘침과 버튼 잘림 없음이 통과했다.

**사용자 수동 확인 체크리스트(아직 하지 않음)**
1. `http://localhost:3000/dev/home`을 열고 시나리오를 고른다(처음에는 추천이 없다).
2. 추천 카드가 시나리오 주제에 맞는지, 카드를 눌러 미리보기, 학습 시작하기, 확인 시트, 리더로 이어지는지 본다.
3. 리더에서 원문 보기(새 탭), 미션과 회고 입력, 새로고침 후 복원, 비운 채 완료를 확인한다.
4. 완료 후 홈으로 가기와 서재(다시 읽기)가 개발용 화면으로 이어지는지 본다. 화면 위 "개발용 확인 화면" 표시가 계속 보여야 한다.
5. "테스트 상태 초기화"로 선택과 완료가 사라지고 같은 시나리오 홈이 다시 시작되는지 본다.
6. "일반 서비스로"를 눌러 실제 홈에 개발용 기록이 보이지 않는지 본다.
